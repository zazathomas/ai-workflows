# Code Simplification

## Goal
After behavior is proven, reduce accidental complexity while preserving exact behavior.

## When to Use

Use after tests are green when code is:

- Hard to read.
- Over-abstracted.
- Duplicated.
- Deeply nested.
- Generated by an agent with unnecessary helpers/layers.
- Carrying dead imports, dead CSS, stale tests, or unused branches.

Skip when simplification would expand scope, when validation is unavailable, or when the current change is already minimal and clear.

## Process

1. Understand why the code exists before changing it.
2. Identify one simplification at a time.
3. Preserve public behavior and API shape.
4. Apply narrowly.
5. Rerun the same tests/validation that proved behavior.
6. Revert simplification if it makes code less clear or changes semantics.

## Common Opportunities

- Replace deep nesting with guard clauses.
- Extract clearly named helpers for repeated concepts, not one-off cleverness.
- Inline unnecessary abstractions.
- Delete dead imports, CSS, tests, fixtures, and compatibility paths only after consumer search.
- Replace nested ternaries with explicit conditionals.
- Use project conventions over personal style.

## React / Frontend Notes

- Avoid deeply nested inline object literals in JSX.
- Extract defaults and render helpers when parser/readability suffers.
- Remove orphan CSS when deleting panels/components.
- Rerun Vite/dev-server or build validation, not just typecheck.

## Output

Summarize simplifications separately from behavior changes so review stays clear.
